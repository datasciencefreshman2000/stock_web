# UI 與前端效能複查

本輪檢查目前 main 的前端查詢、儲存佇列、導覽預載、現金與持倉畫面，直接修正以下問題。未連線操作正式帳務，瀏覽器採本機 production build 與合成 API。

| 問題 | 修正與影響 |
|---|---|
| 現金頁直接載入大型圖表，記帳區被向下推 | 分布圖預設收合，展開才下載圖表程式並繪製，讓記帳區更快出現在頁面上。 |
| 現金儲存後全站 invalidate | 改為只失效摘要、持倉、現金、資金紀錄與校正紀錄；交易歷史與代號清單不因單純現金記帳重新讀取。 |
| 股票持倉同時讀取基金／手動資料 | manual query 僅於手動投資 tab 啟用，避免不必要的 API 請求。 |
| 背景重讀失敗使已有持倉整區消失 | 保留上次成功資料，顯示更新失敗與原地重試；首次無資料失敗仍顯示錯誤。 |
| 換匯切到支出沿用上一模式金額 | 切換記帳種類時清空金額與備註，避免上一模式的數字誤入另一種紀錄；普通換頁、重新整理仍保留同模式草稿。 |
| 桌機數字鍵盤長期佔據大面積 | 改為按需展開，保留一般鍵盤輸入，縮短金額到儲存按鈕的距離。 |
| 導覽預載失敗可能產生未處理 Promise rejection | 預載失敗安靜回復，實際導覽仍走正常載入與錯誤處理。 |

建置比較：現金頁主要 chunk 從上一版約 57.70 kB（gzip 15.99 kB）降至約 31.26 kB（gzip 9.25 kB），約減少 46% 原始大小／42% gzip。分布圖獨立為約 27.47 kB，並將共用約 345 kB 的圖表 chunk 延後到需要時載入；若之前已開過總覽圖表，共用 chunk 可能已在快取。這是程式分包大小，不是實測載入時間或 API 延遲的改善百分比。

驗證：production build 成功、既有前端 4 項測試通過；本機合成資料檢視現金頁、記帳入口、圖表展開與切換種類。沒有執行 Lighthouse、真實手機 CPU／網路節流、多使用者壓測或正式 API 時間量測，因此無法據此宣稱正式網站快幾秒。後端冷快取重建、Supabase 往返與外部報價的實際耗時仍需正式環境量測。

本輪只有前端與文件修改，不需要新的 Supabase SQL；尚未 commit、push 或部署。
